# S8 复盘与 S9 协作约束

> 2026-11-25 定稿，适用于 S9/S10。核心原则：不设固定重试次数；只在“命令行/API 不适合我做、而你操作明显更方便”时请你介入。

## 1. 协作方式：按能力与成本判断，不按系统一刀切

每次遇到需要用户参与的操作，先判断：

1. 是否有受支持、风险可接受、成本合理的 CLI/API/脚本路径？
   - 有：由我完成，不交给用户。
2. 是否必须依赖浏览器 UI、用户账号/2FA、密钥输入、控制台内部功能，或内部 API 不稳定/风险过高？
   - 是：说明原因，准备清楚后请你操作。
3. 是否只是我暂时失败，但命令行仍有合理替代方法？
   - 是：先换方法验证，不直接推给你。

交接触发条件不是“我失败了”，而是“这条路径不适合我，而你在界面上操作明显更方便”。

交接时一次说明：为什么建议你做、具体步骤、预期结果、我后续如何验证、等待期间我继续做什么。等待期间不空转、不重复催问。

Dify 控制台发布/导入只是例子，不是所有 Dify 操作都交给你。服务 API 调用、curl、测试、构建和日志检查仍由我执行。

## 2. 停止无效尝试：不设固定次数

- 不设“三轮”或任何硬性重试次数。
- 同一命令、同一假设不得无变化重复执行。
- 每次尝试应有新信息或新假设；如果连续没有新增信息，且判断命令行路径不可行，就停止并说明。
- 需要及时给出：现象、已验证内容、日志/证据、建议路径、是否需要用户操作。
- 瞬时网络错误或 5xx 可以使用合理退避和有限等待；等待服务启动不算重复尝试，但不能无限等待。

- 是否把命令行/API 可以完成的事错误地交给你；
