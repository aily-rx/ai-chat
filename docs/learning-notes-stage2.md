## 一、概念：带人工确认的 Workflow 状态机

Dify 的 `human_input` 节点把一次 Workflow 分成两个执行阶段：上游节点完成后，运行进入暂停，返回表单、字段值和动作选项；客户端提交表单后，Workflow 从暂停点继续。它不是一个普通的前端弹窗，而是**服务端保存的暂停状态 + 一次性恢复凭据**。

项目中的关键设计：

- **对外只暴露 `runId`，不暴露 `form_token`**。`runId` 是前端查询、确认、导出的业务键；`form_token` 是提交给 Dify 恢复执行的凭据，只保存在后端内存状态中。
- **状态必须显式建模**：`RUNNING`（执行中）、`WAITING_CONFIRM`（等待人工确认）、`RETRYING`（驳回后重新生成）、`SUCCEEDED`（已确认）、`FAILED`（上游/重试失败）、`REJECTED`（二次驳回终态）。状态不只用于展示，还用于权限判断：**只有 `SUCCEEDED` 允许导出**，其余状态返回 `5006`。
- **确认动作要幂等/可拒绝**：非法动作返回 `5005`；过期或已确认的 run 再次确认不会产生新的副作用；重复确认需要明确处理，不能把“点击两次”变成两次流转。
- **确认历史可追溯**：每次状态变化记录时间、动作、traceId，导出时写入“确认记录”，让“谁在什么时候确认了什么”可核验。
- **状态存储的边界**：当前运行状态在后端内存，重启即丢失，这是本阶段的已知限制；生产化应落 MySQL/Redis，并对 `form_token` 加密或使用短期存储。

人工确认不是“加一个按钮”，而是把自动流程切成可审计的两段：机器完成草稿与校验，人承担最终责任，系统负责保证暂停、恢复、拒绝和导出的状态一致。

## 二、踩坑：重试传旧草稿导致“假重新生成”

**现象**：首次驳回后，前端看到 `RETRYING`，随后又回到 `WAITING_CONFIRM`，但耗时只有约 1 秒，草稿几乎没变，节点记录中也没有 `retrieval` 和 `draft_llm`。

**原因**：后端最初把上一版 `draft` 直接作为重试输入。Workflow 的 `intent` 节点判断 `start.draft` 非空时会走“已有草稿”分支，只重跑格式检查和术语检查，跳过检索与生成。也就是说，状态看起来回到了待确认，但业务上并没有按驳回意见重新生成。

**解决**：

1. 重试时把 `draft` 清空，强制 Workflow 走完整链路；
2. 把上一版草稿和用户驳回意见按预算拼进 `task`（总长不超过 2000 字），为生成提供上下文；
3. 后端增加 `RETRYING` 状态、`retryCount` 上限 1 次与二次驳回终态；
4. 重新生成后更新同一 `runId` 的草稿、工具结果、引用和节点快照；
5. 用真实 E2E 断言重试后的节点包含 `retrieval`、`draft_llm`，并在新草稿中检查驳回意见已生效。

**验证**：`scripts/regression/workflow_e2e.py` 17/17 步通过；W4 复跑中重试后草稿从 872 字变为 1301 字（生成内容会波动，此前 FR-13 运行为 1128→1335），引用 3 条，`retryCount=1`；二次驳回进入 `REJECTED` 且导出返回 `5006`；后端全量 104/104 测试通过。PR/评审记录中的 FR-10 即此次修复。另于 2026-11-26 用 headless Chrome 走通页面链路：发起→`WAITING_CONFIRM`（16 节点）→修改后通过→`SUCCEEDED`→实际下载，工具结果需等前端 5 秒轮询后才显示；同一轮还验证了“驳回→重新生成中→待确认（草稿 1325→1995 字、`retryCount=1`）→再次驳回→已驳回、导出 5006”。Workflow 页面不画引用卡片，引用要在视图 API 或导出文件中核验。

**复用教训**：做“重试/重新生成”时，不能只改状态字段；必须确认**上游输入是否与首次执行等价**。如果输入让流程走了捷径，状态机再正确也只是假动作。

## 三、待验证问题：检索阈值与召回率的平衡

**问题**：最终评测中 A/B 均达到硬指标，但引用里仍混入低相关文档。B 库 q01、q02 各有 2 条无关引用，q10 有 1 条；A 库 q01、q02、q10 各 1 条。低分文档相似度约 0.43–0.51，Dify TopK=4 仍将其返回。

**为什么不能直接调高阈值**：提高相似度阈值或降低 TopK 可能过滤掉低分但正确的文档，尤其 q05、q07 等关键事实题；如果同时修改检索和生成，无法判断指标变化来自哪一环。BC-02 暂未修改，是刻意控制变量。

**下一步实验设计**：

1. 固定题目、模型、Embedding 和评测脚本；
2. 只改一个变量：先尝试相似度阈值（如 0.55），保持 TopK=4；
3. 复测命中率、拒答率、引用完整率、无关引用题数；
4. 若命中率下降，再单独比较 TopK=3 或混合检索/Rerank；
5. 保留每次的原始 SSE、逐题结果与汇总，失败也写入报告。

**判定标准**：硬指标不得下降（命中 ≥10/10、拒答 5/5、引用完整 10/10），同时无关引用题数下降，才把阈值变更作为默认配置；否则保留现状并把阈值作为可配置项。

## 四、补充：本阶段形成的评测口径

- **命中**：回答包含全部预期关键事实，且至少一条引用指向 `expectedDoc`；只答对事实但没有正确引用不算命中。
- **拒答正确**：`citations` 为空、收到 `done`、无错误，且回答明确拒答；不能把“没检索到但模型编答案”计为通过。
- **引用完整**：非拒答回答至少 1 条有效引用，且 `docName`、`segmentIndex`、`excerpt` 齐全；`page=null` 是 Dify 数据限制，不伪造页码。
- **证据留存**：原始 SSE、逐题 JSONL、汇总 JSON、导出文件与回归日志全部落盘；报告只写运行结果，不按结果改题。
