## 一、概念：SSE（Server-Sent Events）

SSE 是服务器通过单向 HTTP 长连接持续向客户端推送事件的机制。每个事件由 `event` 和 `data` 组成，适合大模型逐字返回的场景。

项目中，后端使用 Spring 的 `SseEmitter` 转发 DeepSeek 的流式结果；前端不能用 `EventSource` 发送 POST 请求，因此使用 `fetch + ReadableStream` 手动解析流。每个请求必须以 `done` 或 `error` 事件结束，否则前端无法区分正常完成和连接中断。

## 二、踩坑：SSE 中文乱码

**现象**：接口在浏览器中正常，但 MockMvc 测试读取中文时出现乱码。

**原因**：测试端默认按 ISO-8859-1 解码响应，而 SSE 实际是 UTF-8。

**解决**：

- 后端 SSE `produces` 显式声明 `text/event-stream;charset=UTF-8`；
- 测试侧按 UTF-8 读取响应体；
- 增加对应测试，避免后续回归。

**验证**：`ChatControllerTest` 中 SSE 响应中文断言通过，前端浏览器流式输出正常。

## 三、待验证问题：结构化抽取稳定性

**问题**：结构化抽取不仅依赖模型调用，还依赖输出清洗、JSON 解析、字段校验和失败重试。单次样例通过，不代表批量文档稳定。

**当前措施**：

- 抽取请求固定 `temperature=0.0`；
- 剥离 Markdown 围栏后再解析 JSON；
- 解析失败重试 1 次；
- 仍失败返回 `5003`，模型调用失败返回 `5001`。

**下一步验证**：用 20 段不同类型公文连续抽取，统计首次解析成功率、重试率和失败原因，目标是将首次解析成功率稳定在可接受范围，并保留 badcase 记录。
